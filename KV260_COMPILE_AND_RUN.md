# KV260 compile and run demo

This guide builds and runs the repository's `conv2d_kernel` on a Kria KV260.
It covers three separate products:

1. An FPGA kernel and matched Kria firmware application, built on an x86-64
   Linux machine with Vitis/Vivado/PetaLinux 2022.1.
2. An AArch64 YOLO model, XRT runtime, and host programs, cross-compiled on
   macOS.
3. The installed application and runtime on the KV260.

These products are related, but they are not interchangeable. In particular,
an `.xclbin` by itself is not a complete KV260 `XRT_FLAT` application.

## End-to-end flow

```text
x86-64 Vitis machine
  Conv2DKernel.cpp
    -> conv2d_kernel.hw.xo
    -> matched .xclbin + .bit.bin + .dtbo + shell.json

macOS
  YOLOv5n ONNX + MyAccel + AArch64 sysroot + KV260 XRT snapshot
    -> yolo-myaccel-driver-aarch64
    -> yolov5n-myaccel-aarch64.so
    -> host_xrt_conv_test
    -> deployment archive

KV260
  install firmware -> activate with xmutil -> verify XRT
    -> probe-only test -> tiny Conv test -> optional full YOLO
```

## Requirements

### Vitis build machine

- x86-64 Linux
- AMD Vitis, Vivado, and PetaLinux 2022.1
- The final KV260 `kv260_ispMipiRx_vcu_DP` platform `.xpfm`
- This repository, including its ONNX-MLIR submodule

The KV260 is the runtime target. Do not attempt to run `v++` on the board or
on the macOS development machine.

### macOS cross-compile machine

- Clang/LLVM with `ld.lld`
- Python 3 and `make`
- The Ubuntu 22.04 AArch64 sysroot generated by this repository
- XRT headers matching the board
- The board-compatible AArch64 `libxrt_coreutil.so`
- A native ONNX-MLIR compiler built with `MyAccel`

### KV260

- Ubuntu 22.04
- XRT 2.13.x, matching the checked-in development assumptions
- `xmutil`, `xbutil`, and sudo access
- SSH access from the macOS machine

## 1. Initialize the repository

Run this once on each build machine:

```sh
git submodule update --init --recursive
```

The HLS kernel is:

```text
third_party/onnx-mlir/src/Accelerators/MyAccel/Runtime/Conv2DKernel.cpp
```

The kernel entry point is named `conv2d_kernel`.

## 2. Locate the KV260 Vitis platform

On the x86-64 Vitis machine:

```sh
cd ~/capstone-compiler
source /opt/Xilinx/Vitis/2022.1/settings64.sh

v++ --version
platforminfo -l
```

If `platforminfo -l | grep -i kv260` prints nothing, check the known locally
built platform directly:

```sh
ls -l \
  "$HOME/xilinx-platforms/kria-vitis-platforms/kv260/platforms/xilinx_kv260_ispMipiRx_vcu_DP_202210_1/kv260_ispMipiRx_vcu_DP.xpfm"
```

If the file exists, use its absolute path even when it is not registered in
Vitis's platform repository:

```sh
export KV260_PLATFORM="$HOME/xilinx-platforms/kria-vitis-platforms/kv260/platforms/xilinx_kv260_ispMipiRx_vcu_DP_202210_1/kv260_ispMipiRx_vcu_DP.xpfm"
platforminfo "$KV260_PLATFORM"
```

Use the final platform under
`platforms/xilinx_kv260_ispMipiRx_vcu_DP_202210_1/`. Do not use an
intermediate `.xpfm` under `platforms/xsct/`.

If no final `.xpfm` exists, build the 2022.1 Kria platform first:

```sh
mkdir -p "$HOME/xilinx-platforms"
cd "$HOME/xilinx-platforms"

git clone \
  --branch xlnx_rel_v2022.1 \
  --recursive \
  https://github.com/Xilinx/kria-vitis-platforms.git

cd kria-vitis-platforms/kv260
make platform PFM=kv260_ispMipiRx_vcu_DP
```

## 3. Compile the FPGA kernel

Return to the repository root on the Vitis machine:

```sh
cd ~/capstone-compiler
source /opt/Xilinx/Vitis/2022.1/settings64.sh
mkdir -p build/kv260-hls
```

Compile the C++ kernel into a Vitis hardware object:

```sh
v++ --compile \
  --target hw \
  --platform "$KV260_PLATFORM" \
  --kernel conv2d_kernel \
  --include third_party/onnx-mlir/src/Accelerators/MyAccel/Runtime \
  third_party/onnx-mlir/src/Accelerators/MyAccel/Runtime/Conv2DKernel.cpp \
  --output build/kv260-hls/conv2d_kernel.hw.xo
```

Link the object into a hardware `.xclbin` at 100 MHz:

```sh
v++ --link \
  --target hw \
  --platform "$KV260_PLATFORM" \
  --clock.defaultFreqHz 100000000 \
  build/kv260-hls/conv2d_kernel.hw.xo \
  --output build/kv260-hls/conv2d_kernel.hw.xclbin
```

Verify the result:

```sh
ls -lh build/kv260-hls/conv2d_kernel.hw.{xo,xclbin}

xclbinutil --info \
  --input build/kv260-hls/conv2d_kernel.hw.xclbin
```

Confirm that the metadata reports:

- `conv2d_kernel`
- hardware content
- the KV260 `ispMipiRx_vcu_DP` platform
- a 100 MHz kernel clock

The repository also contains `scripts/build_kv260_conv2d_xclbin.sh`, but its
current link command does not set the required 100 MHz clock. For a reproducible
demo, use the explicit commands above.

## 4. Build the matched Kria firmware application

The board application must contain these four non-empty files with a common
basename:

```text
build/kv260-firmware/conv2d-kv260/
  conv2d-kv260.bit.bin
  conv2d-kv260.dtbo
  conv2d-kv260.xclbin
  shell.json
```

Their purposes are:

- `conv2d-kv260.bit.bin`: FPGA configuration bitstream.
- `conv2d-kv260.dtbo`: matching device-tree overlay, including FPGA and ZOCL
  nodes.
- `conv2d-kv260.xclbin`: XRT kernel image and metadata.
- `shell.json`: manifest used by `xmutil`.

The `.bit.bin`, `.dtbo`, and `.xclbin` must come from the same Vitis/Vivado
link output. Never combine a DTBO or bitstream from another Kria application
with this `.xclbin`.

Create `shell.json` as:

```json
{
  "shell_type": "XRT_FLAT",
  "num_slots": "1"
}
```

Generate the `.bit.bin` from the linked `system.bit`:

```sh
printf 'all:{system.bit}\n' > bootgen.bif
bootgen -w -arch zynqmp -process_bitstream bin -image bootgen.bif
```

Generate the DTBO from the XSA that matches the same Vitis link output.
Prefer the PetaLinux 2022.1 `fpgamanager_dtg` flow. Do not create a generic
overlay or copy one from an unrelated application. The detailed firmware
generation and validation checklist is in:

```text
scripts/kv260_firmware_build_prompt.md
```

Validate the completed directory before deployment:

```sh
xclbinutil --info \
  --input build/kv260-firmware/conv2d-kv260/conv2d-kv260.xclbin

dtc -I dtb -O dts \
  build/kv260-firmware/conv2d-kv260/conv2d-kv260.dtbo \
  -o build/kv260-firmware/conv2d-kv260/conv2d-kv260.roundtrip.dts

sha256sum \
  build/kv260-firmware/conv2d-kv260/conv2d-kv260.bit.bin \
  build/kv260-firmware/conv2d-kv260/conv2d-kv260.dtbo \
  build/kv260-firmware/conv2d-kv260/conv2d-kv260.xclbin \
  build/kv260-firmware/conv2d-kv260/shell.json
```

Copy the complete firmware directory back into the same path in the macOS
checkout.

## 5. Prepare the board-compatible XRT snapshot on macOS

The macOS cross-linker needs target XRT headers and the AArch64 XRT library.
The expected local layout is:

```text
toolchains/kv260-xrt-2.13.0/
  include/xrt/
    xrt/xrt_bo.h
    xrt/xrt_device.h
    xrt/xrt_kernel.h
  lib/
    libxrt_coreutil.so
    libxrt_coreutil.so.2
    libxrt_coreutil.so.2.13.0
```

This directory is ignored by Git. A fresh clone will not contain it. Copy the
matching headers and `libxrt_coreutil.so*` from the KV260 or from a matching
AArch64 XRT development package.

Discover their source paths on the board with:

```sh
xbutil --version

find /usr /opt/xilinx \
  -type f -path '*xrt*' -name 'xrt_bo.h' 2>/dev/null

ldconfig -p | grep libxrt_coreutil
```

Preserve the library symlinks when copying. On macOS, verify that the copied
library is for the target rather than the host:

```sh
file toolchains/kv260-xrt-2.13.0/lib/libxrt_coreutil.so
```

Expected architecture:

```text
ELF 64-bit ... ARM aarch64
```

## 6. Cross-compile the runtime on macOS

From the repository root:

```sh
make sysroot-jammy

export MYACCEL_USE_XRT=1
export AARCH64_XRT_ROOT="$PWD/toolchains/kv260-xrt-2.13.0"
export AARCH64_XRT_INCLUDE_DIR="$AARCH64_XRT_ROOT/include/xrt"
export AARCH64_XRT_LIB_DIR="$AARCH64_XRT_ROOT/lib"

make cross-yolo-accelerator-aarch64
```

This produces:

```text
build/yolo-myaccel-driver-aarch64
build/yolov5n-myaccel-aarch64.so
build/bus-input-aarch64.bin
```

Verify that the executable and shared library are AArch64 ELF files:

```sh
file build/yolo-myaccel-driver-aarch64
file build/yolov5n-myaccel-aarch64.so
```

The AArch64 sysroot also needs UUID runtime and development files. The current
`make sysroot-jammy` flow includes `libuuid1` and `uuid-dev`.

This stage creates the ARM software. It does not create the FPGA `.xclbin`.

## 7. Build, package, and install from macOS

The deployment helper cross-builds the XRT-enabled runtime and standalone host
test, packages the runtime libraries and firmware, uploads the archive, and
installs it on the board:

```sh
KV260_REMOTE=ubuntu@BOARD_IP \
./scripts/build_package_deploy_kv260_runtime.sh \
  --firmware-dir build/kv260-firmware/conv2d-kv260 \
  --firmware-app conv2d-kv260
```

Replace `BOARD_IP` with the board's hostname or address. The default runtime
installation directory is:

```text
/home/ubuntu/dev/runtime
```

The firmware is installed under:

```text
/lib/firmware/xilinx/conv2d-kv260
```

The helper intentionally leaves firmware activation explicit unless
`--activate-firmware` is provided. For a live demo, activate it manually so
each step remains visible.

If the board does not allow passwordless sudo, provide `KV260_PASSWORD` to the
helper without committing or recording the password in the repository.

## 8. Activate the application on the KV260

Connect to the board:

```sh
ssh ubuntu@BOARD_IP
```

List, unload, and activate the application:

```sh
sudo xmutil listapps
sudo xmutil unloadapp
sudo xmutil loadapp conv2d-kv260
sudo xmutil listapps
```

Confirm that `conv2d-kv260` is active. Then verify the XRT device:

```sh
xbutil examine
ls -l /dev/dri/renderD128 /dev/zocl 2>/dev/null
```

Do not continue unless `xbutil examine` reports the device as ready and a
usable XRT device node exists.

## 9. Run the standalone FPGA tests

Enter the installed runtime directory:

```sh
cd /home/ubuntu/dev/runtime
```

First, test only device and kernel setup:

```sh
./host_xrt_conv_test \
  ./conv2d_kernel.hw.xclbin \
  --probe-only
```

Expected ending:

```text
[host-xrt-test] XRT setup completed
[host-xrt-test] probe-only requested; exiting before kernel launch
```

Next, run the default tiny `1x1x4x4` convolution:

```sh
./host_xrt_conv_test ./conv2d_kernel.hw.xclbin
```

Expected result:

```text
PASS case=tiny max_abs_diff=...
```

The FPGA output is compared with a CPU reference using a tolerance of `1e-4`.
Only after the tiny test passes should both tiny and medium tests be run:

```sh
./host_xrt_conv_test ./conv2d_kernel.hw.xclbin --all
```

The host test defaults to a 30-second total alarm and a 5-second kernel wait.
They can be adjusted for diagnosis:

```sh
HOST_XRT_TIMEOUT_SEC=60 \
HOST_XRT_RUN_TIMEOUT_MS=10000 \
./host_xrt_conv_test ./conv2d_kernel.hw.xclbin
```

## 10. Run full YOLO with guarded XRT routing

From the board runtime directory:

```sh
cd /home/ubuntu/dev/runtime

export MYACCEL_XCLBIN="$PWD/conv2d_kernel.hw.xclbin"
export LD_LIBRARY_PATH="$PWD:$PWD/runtime-libs"
unset MYACCEL_FORCE_CPU

./yolo-myaccel-driver-aarch64 \
  ./bus-input-aarch64.bin \
  ./bus-myaccel-xrt.bin
```

Expected high-level result:

```text
output shape: [1, 25200, 85]
best raw candidate: ...
```

The default safety limits are:

```text
MYACCEL_MAX_OUTPUT_PIXELS=6400
MYACCEL_MAX_IO_BYTES=33554432
```

Convolutions exceeding either limit fall back to the CPU. Therefore, the
normal full-model run may use both FPGA and CPU execution. This is intentional:
the current kernel is correctness-oriented and not yet optimized for large
YOLO layers.

Do not disable these guards during a teammate demo. Setting either limit to
`0` disables that guard and may allow a very long FPGA execution.

## 11. Force the CPU reference path

Use the same AArch64 model and driver while bypassing XRT for every Conv:

```sh
cd /home/ubuntu/dev/runtime
export LD_LIBRARY_PATH="$PWD:$PWD/runtime-libs"

MYACCEL_FORCE_CPU=1 \
./yolo-myaccel-driver-aarch64 \
  ./bus-input-aarch64.bin \
  ./bus-myaccel-cpu.bin
```

The runtime should report a fallback reason similar to:

```text
MYACCEL_FORCE_CPU is set
```

`MYACCEL_FORCE_CPU` is presence-based. This still forces the CPU:

```sh
MYACCEL_FORCE_CPU=0 ./yolo-myaccel-driver-aarch64 ...
```

Return to normal guarded XRT routing with:

```sh
unset MYACCEL_FORCE_CPU
```

The standalone `host_xrt_conv_test` always exercises XRT directly and is not
affected by `MYACCEL_FORCE_CPU`.

## 12. Demo order

For a reliable live demonstration, use this order:

1. Show the kernel source and the `.xo -> .xclbin` Vitis flow.
2. Show the four matched firmware files.
3. Show the macOS AArch64 runtime artifacts with `file`.
4. Install and activate `conv2d-kv260`.
5. Show `xbutil examine` reporting a ready device.
6. Run `--probe-only`.
7. Run the tiny Conv test and show `PASS`.
8. Run forced-CPU YOLO as a stable software baseline.
9. Optionally run guarded XRT YOLO and explain per-layer CPU fallbacks.

The tiny Conv `PASS` is the clearest proof that the full stack works:

```text
matched firmware + XRT device + loaded xclbin + opened kernel
  + buffer transfers + kernel execution + CPU-reference comparison
```

## Troubleshooting

### `platforminfo -l | grep -i kv260` prints nothing

Use the final `.xpfm` by absolute path. It does not need to appear in the
registered platform list when `v++ --platform` receives the path directly.

### `v++` is not found

The command must run on the x86-64 Linux Vitis machine after sourcing:

```sh
source /opt/Xilinx/Vitis/2022.1/settings64.sh
```

### `load_xclbin()` hangs or the board stops responding

Stop the test. Verify that the active `xmutil` application contains the
`.bit.bin`, `.dtbo`, and `.xclbin` from the same link output. Deploying only an
`.xclbin`, or mixing it with another platform's active firmware, is unsafe.

### No XRT device node exists

Check:

```sh
sudo xmutil listapps
xbutil examine
dmesg | tail -100
```

Do not run the host test until the application is active and the XRT device is
ready.

### macOS cannot find XRT headers

The include root should be:

```text
toolchains/kv260-xrt-2.13.0/include/xrt
```

and this file must exist:

```text
toolchains/kv260-xrt-2.13.0/include/xrt/xrt/xrt_bo.h
```

### macOS links the wrong architecture

Verify the target library:

```sh
file toolchains/kv260-xrt-2.13.0/lib/libxrt_coreutil.so
```

It must be an AArch64 ELF library, not a macOS Mach-O library or an x86-64
ELF library.

### The board cannot load a shared library

From `/home/ubuntu/dev/runtime`:

```sh
export LD_LIBRARY_PATH="$PWD:$PWD/runtime-libs"
ldd ./yolo-myaccel-driver-aarch64
```

Inspect the exact model library path reported by `ldd`; do not diagnose a
duplicate or stale copy elsewhere.
